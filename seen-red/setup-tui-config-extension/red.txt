ONE DEFECT THIS FIXTURE'S OWN BUILD CAUGHT (named per this project's own "claims carry
witnesses" discipline): the first draft of case (e) read the outer `state` dict after driving
Pilot interactions and found every field still at its DEFAULT value, even though the widgets
themselves visibly changed (RadioSet.pressed_index moved, Input.value changed) -- root cause:
`tools.configtree.app.ConfigTreeApp.__init__` shallow-copies its `initial_state`
(`self.state = dict(initial_state or {})`), so a NEW top-level key (`"_live_fields"`) created
by the running app's own write-through lands on `app.state`'s OWN dict, invisible from the
fixture's outer `state` variable -- the exact silent-divergence class ADR-0012 P1 warns about,
here between two dict OBJECTS rather than two functions. FIXED (not by reading `app.state`
instead, which would only move the coupling, but by pre-seeding `state["_live_fields"] = {}`
before `build_app` -- the shallow copy then shares that ONE nested dict object by reference, the
same trick seen-red/setup-tui-config-file's own case v already relies on for its own overrides
dict, now named explicitly here for the next fixture author who hits this).
