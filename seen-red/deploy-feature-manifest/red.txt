Work item deploy-feature-manifest (ledger row 1274/1322, maintainer verdict row 1274 "as
recommended"): a DECLARATIVE FEATURE MANIFEST bootstrap/new-project.sh itself reads and applies
-- portable ADRs (mirrors the existing --no-law flag), vendored skills (new opt-out), the panel

FORMAT DECISION: a new file, `features.json`, beside deployment.json in the scaffold -- NOT an
extension of `.claude/apparatus.json`. USER-CONFIGURATION.md's own words scope apparatus.json to
ONE closed vocabulary (per-mechanism enforce/observe/off switches for safety mechanisms this
project ships); a scaffold-time inclusion decision is a different kind of fact (WHAT got born,
not HOW HARD an already-born mechanism polices itself), and folding it into apparatus.json would
widen that file's own unknown-key sweep (gates/apparatus_unknown_keys.py) to a class it was
never written to reason about. `features.json` is hand-editable, self-describing keys, no
comments needed to use it (tools/setup_tui/steps_features.py's own module docstring has the full
account, including why this is ALSO not the same file as the wizard's own self-application
`world-config.toml`).

THREE real defects this fixture's own build caught and fixed before banking (named per this
project's own "claims carry witnesses" discipline, not silently smoothed over -- the third is
the more instructive one: a fix that LOOKED like it worked, on this fixture's own first honest
green run, until a separate manual process-residue audit caught it):
  - `git clone --local` (no `--no-hardlinks`) fails outright ("Invalid cross-device link")
    whenever <dest-dir> is on a different filesystem/mount than the autoharn checkout --
    witnessed live against a /tmp scratch dest. Fixed: `--no-hardlinks` added (still zero-
    network; forces a real copy instead of a hardlink attempt).
  - `led register-principal` (case 5) auto-spawns the boundary service (ensure-running) -- a
    live process outliving the fixture's own scope unless explicitly stopped.
  - FIRST FIX ATTEMPT WAS WRONG, AND THE FIXTURE DID NOT CATCH IT: `autoharn service stop`
    called with `cwd=dest` (reasoning: "it must resolve the target from its own directory,
    like the scaffolded shims do") APPEARED to work -- exit 0, no assertion on it, fixture
    reported "zero residue". A separate manual `pgrep -af boundary_service` audit, run AFTER
    this fixture's own "all cases PASS" line, found FOUR orphaned boundary_service processes
    still running (two from this fixture's own earlier case-5 runs, two from a sibling
    fixture's own live-birth case) -- `libexec/autoharn-service`'s own `DEPLOYMENT_PATH`
    resolves from the `PICKUP_DEPLOYMENT` ENV VAR (defaulting to THIS AUTOHARN CHECKOUT'S OWN
    deployment.json), never from cwd -- so the "stop" call was silently stopping nothing
    (refusing against the wrong, autoharn-root deployment) while a real orphan kept running
    at the scratch world's own port. FIXED: `PICKUP_DEPLOYMENT=<dest>/deployment.json` passed
    as an explicit env var, AND the fixture now asserts the stop call's own exit code and
    output (case5's own new "boundary service stopped" row) instead of trusting silence --
    re-run live: the specific pid is confirmed gone via `pgrep` immediately after.
