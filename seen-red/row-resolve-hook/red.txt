APPENDIX 2026-07-26 -- a SECOND, real (not mutation-injected) finding in this same shipped hook,
from a CLEARED-BUT-MODERATE-SILENT review of `hooks/userpromptsubmit_row_resolve.py` at fe7d461
(the commit this whole seen-red family is built against, unmodified this time -- no deliberate
mutation needed, the bug was already there).

FINDING: `_ROW_PROMPT_RE = re.compile(r"^/row\s+\d+(\s+\d+)*\s*$")` uses `\s`, which matches
`\n` as well as space/tab. Python's `re.match` (no `re.MULTILINE`) additionally lets a plain
`$` anchor at either end-of-string OR immediately before a trailing `\n`. Combined, an ordinary
TWO-LINE prompt whose second line happens to be pure digits -- e.g. the literal prompt
"/row 5\n6" (a user typing "/row 5" on one line and something starting with "6" on the next,
with no intent to invoke this hook at all) -- matched the "whole prompt" anchor and was silently
BLOCKED and replaced with a row dump, exactly the "hook that mangles an ordinary prompt is worse
than no hook" hazard design constraint 2 names (and the same class of bug g-mixed-request-not-
matched already proves for the single-line case: an anchor gap letting real user text through
the /row net uninvited).

Direct demonstration (real hook at fe7d461, unmodified, no mock CLI needed to see the wrong
classification -- the deployment.json refusal text itself proves the prompt was captured),
stdin:

    {"hook_event_name":"UserPromptSubmit","session_id":"fixture","cwd":"/tmp","prompt":"/row 5\n6"}

stdout (verbatim, the actual red output, fe7d461):

    {"decision": "block", "reason": "/row resolved locally via `.../autoharn led show <id>`
    -- no model turn spent.\n\nrow 5: led: deployment record not found at
    .../deployment.json -- a project with no deployment record is refused, never silently
    un-resolved. ...\nrow 6: led: deployment record not found at .../deployment.json ..."}

The user's real second line ("6") was consumed as a second row id and never reached the model
at all -- the exact zero-cost-guarantee inversion the module docstring's own LATENCY HAZARD
section worries about for a different mechanism (hook timeout), now shown for the matcher
itself.

FIX: `extract_row_ids` now rejects any EMBEDDED newline before the anchored regex ever runs

pattern text itself is left unchanged (module docstring's MATCHING section quotes it verbatim),
so the fix lives at the guard, not hidden inside the regex.

TRAILING-NEWLINE RULING: a prompt that is otherwise a pure `/row <id> [...]` command plus
exactly ONE trailing newline and nothing after it (case i-trailing-newline-matched,

produce) carries no additional content past the command: judged still a match, and resolved
same as "/row 5". Only a genuine second line -- digits (h) or blank (j) -- is pass-through.
