## Leg 1 — The precedence violation

**WITNESSED: the underlying mechanism gap is real, named explicitly, and reproduced twice in the ledger. I could NOT find a ledgered specimen that matches the maintainer's exact description ("an orchestrator started an agent in the wrong order, violating precedence constraints") as a single, self-contained incident — this is reported as a genuine miss, not papered over.**

What I searched: the full `led standing` dump (durable decisions), `led --recent` widened to 1836 in-force rows (covering ~2026-07-16 → today), every `work_depends_on:` edge in that window with its claim/close chronology, `led work violations` (empty — no open violations right now), commit messages since 2026-07-28 (`git log --since=2026-07-28 --all`), and doc-tree grep for "precedence". None produced a row reading like "agent X started before Y closed, violating a blocks-close edge."

What the mechanism actually is, confirmed from CLAUDE.md and multiple ledger rows:

- `led work depends <slug> <on-slug> --type blocks-close|informs` records a precedence edge. `informs` (the default) is context only — **never enforced**. `blocks-close` is enforced, but **only at `--strict close`, i.e. it gates the antecedent's dependent from CLOSING, not from STARTING** (CLAUDE.md point 1, verbatim: "an informs-only precedence constraint is a fact nothing mechanical will ever refuse").
- This exact gap was hit and named twice in-session, both self-caught (not maintainer-witnessed at the moment):
  - Row 887: "three distinct kinds of waiting, which the startable view cannot distinguish because blocks-close gates CLOSING and not STARTING."
  - Row 1176/1185 (reservation on a review): "'led work startable' still lists the blocked Moves, because blocks-close gates CLOSE and not START by the kernel's own design... That is exactly the 'an informs-only precedence constraint is a fact nothing mechanical will ever refuse' hazard... arrived at from the other direction."
  - Row 911 (assumption, self-caught before dispatch): a real, confirmed precedence between `panel-page-tie-pagination-safety` (895) and its two dependents (901, 902) existed in prose only, with **no** `blocks-close` edge recorded — "Proceeding on the assumption the maintainer wants this formalized," which produced rows 913/914 retroactively. In that instance the actual dispatch order (row 1036, wave-6) happened to be correct because the antecedent had already shipped (row 1011) before the dependents were dispatched — so this was a near-miss caught before harm, not the maintainer-witnessed incident.

**Candidate specimens closer to "wrong order, maintainer caught it directly":**

- **Row 1347** (2026-07-30): "the wave-A dispatch (4 agents...) was scheduled by my own manual file-overlap judgment, NOT the makespan-scheduler — despite it being a MANDATED resource (row:147) for driving 3+ claimed work items under resource-conflict... constraints, which this exactly was. **Maintainer caught this directly.**" This is a resource-conflict scheduling lapse (not using the mandated tool), not a directed-precedence violation, and the manual judgment happened to be correct this time — but it is the closest maintainer-witnessed, ledgered specimen of "the orchestrator scheduled agents without the tool that would have gotten the order right."
- **Row 1451** (2026-07-30), SEVERE, maintainer-caught: an agent was dispatched to modify autoharn's own checkout (`tools/setup_tui/data/config_schema.toml`, worktree commit `c3f53eaa`) — autoharn-panel has **no standing** to touch autoharn's tree at all. Discarded completely. This is an authorization-scope violation, not a precedence-order one, but is the single most serious maintainer-caught dispatch defect in the window and belongs in the same "orchestrator dispatched wrongly" family the commission is pointing at.

**The "earlier instance" (repeat), found pre-window:** commit `29e7d5b` (2026-07-16, `fix(process): correct stale makespan-scheduler precedence caveat; use real tool for backend-remediation batching`): "A hand-computed batching for the backend-remediation decomposition leaned on that stale claim [that the scheduler couldn't natively encode directed precedence] instead of checking the tool's actual current capability... **Caught by direct challenge, not self-caught.**" This is the same failure shape as row 1347 — an orchestrator hand-computing dispatch order instead of using the mandated precedence/scheduling tool, twice caught by the maintainer directly, five weeks apart. If this is what "once again" refers to, the pattern is: the mandated makespan-scheduler tool exists specifically to prevent hand-judgment ordering errors, and the orchestrator keeps reverting to hand judgment under time/quota pressure, only corrected when the maintainer notices.

**What would have caught a true precedence violation, and didn't:** nothing on the panel side refuses a worker from *starting* on a dependent item early; `led work violations`/`work_item_violations` is a real, wired, and consumed view (`panel-work-startable-and-violation-history`, shipped and independently reviewed at row 1096) — but it also only surfaces **existing** violations after the fact via a drawer a human has to look at, it does not block dispatch. This is a genuine, currently-open substrate gap: **there is no mechanical refusal at dispatch time for starting work against an unmet `blocks-close` antecedent** — only a post-hoc "did I close in violation" check. autoharn itself should note this as a live gap in its own orchestration doctrine, since the same `led work` verb set and the same `blocks-close`/`informs` split is autoharn's own kernel design, not something panel invented.

## Leg 2 — The new GUI-surface auditing machinery

**WITNESSED**, and it is real, but "sufficiently robust to stand down systematic GxP audits" needs one caveat stated back plainly: **the newest mechanized gate still missed a defect the maintainer found by eye, on its sixth consecutive pass, one round before the window this spy covers.**

What the machinery actually is (files, live in the repo):

- **`frontend/e2e/geometry-containment.spec.ts`** + **`frontend/e2e/support/text-geometry.ts`**: a selector-free DOM-walk assertion (`assertNoTextGeometryOverflow`) checking element-vs-parent AND element-vs-**sibling** text-geometry containment — this is the mechanism born specifically to close the class of defect ("timestamp visually sits on top of adjacent statement text") that six successive Opus audit passes missed because they only checked element-vs-page. It sweeps every tab (26-entry `support/tabs.ts` SSOT) across three viewport widths, both the plain-`<table>` and virtualized-grid render paths (`DataTable.vue`'s `VIRTUALIZE_AT_OR_ABOVE` threshold), and — added later, after `panel-geometry-gate-cannot-exercise-its-class` (row 1570, a REFUTED prior claim, row 1569) — a wide-viewport case with real (non-em-dash) content, since the original sample never exceeded 768px and so never exercised the side-by-side plain-table layout the founding defect actually lived in.
- **Five lint gates wired into `npm run build`**: `lint-boundaries.mjs` (layering: services < state < composables < components, upward imports denied), `lint-flex-shrink.mjs`, `lint-no-hand-query.mjs` (bans hand-built query strings; caught red/green on a seeded violation), `lint-no-sleep.mjs` (bans `waitForTimeout` in e2e outside an allowlist), `lint-token-adoption.mjs` (design-token adoption, colour axis catches hex/rgb outside `tokens.css`). Per `r2-gate-universe-discipline` (row 2097, closed row 2188), every gate now records at its own header "the widest-universe question — what this check could cover at similar cost and what is deliberately left out" — a propagation discipline against gates drawn narrowly at the provoking-instance's width, itself a lesson from a named prior failure (row 2200's meta-diagnosis).
- **A responsiveness/DPI/browser e2e matrix**: Firefox added alongside Chromium, a high-DPI 4K profile, a write-mode-armed variant (`panel-e2e-matrix-browsers-dpi`, shipped, row 2062) — because the earlier gates were Chromium-only/three-viewport/read-only and missed a maintainer-witnessed occlusion that only reproduced at wide/4K rendering.
- **Periodic Opus-authored audits** (not mechanized — a human-in-the-loop instrument, re-run with the byte-identical prompt each round for before/after comparability): six consecutive "comprehensive responsiveness audit" passes (`docs/consults/2026-07-*-comprehensive-responsiveness-audit-*`), plus paired ADR-0010/0012 compliance and "enterprise professionalism" Opus consults, now run in **rounds** (round-2 versions exist at `docs/consults/2026-07-31-opus-*-round2`) as a deliberate before/after discipline.
- **Deferred, not yet built**: `panel-ui-affordance-tree` (row 2112, explicitly NOT claimed, deferred "after the round-2 remediation program") — mechanically deriving the UI's own affordance tree (router-links, `@click` handlers, destinations per view) via SFC/AST extraction, to be served to audit dispatch prompts as the interaction-coverage universe so "an unclicked affordance class can no longer hide from a review because the reviewer picks what to click." This is the piece that would close the class of miss below, and it does not exist yet.

**What it provably does NOT cover, stated by the machinery's own authors, on the record:**

- Row 1119 (2026-07-30): "the 6th audit did NOT find the timestamp-overflow defect the maintainer observed by eye... a SIXTH consecutive miss, which makes the ADR-0000 question one about the audit method (Rule 2b, the net) and not about the column." The geometry-containment gate above was minted specifically in response to this — so the newest mechanism is a direct repair of a documented six-pass blind spot, not a speculative improvement.
- Row 1488: two of the gates minted the round *before* were themselves "blind to F1 by construction" — they set the viewport to the exact width where a nav element measures ~1px, but assert on `#main-content`, the complement of the element the earlier fix actually changed. "A gate that visits the crime scene and looks the other way."
- Row 2186 (blocking finding, sprint-3, fixed same day at `4f7954c`): the new `datatable-uniform-chrome.spec.ts` asserted export **button presence** but never export **content** — the witness gap that let a real corruption (presentation-wrapper objects serialized into CSV/JSON instead of raw data) through undetected.
- Row 2200 itself: "Round-3 audit reminder stands (**commissioner directive**)" — i.e. the maintainer's own standing instruction as of the last recorded audit cycle was that a further systematic round is still owed, which sits in tension with (not necessarily contradicting, since it predates) this commission's instruction to stand audits down. Worth flagging back to the maintainer as a possible open loop rather than silently resolving it either way.

**autoharn-side takeaway**: what superseded the systematic GxP audit series is not one artifact but three layers with different miss-classes: (a) mechanical gates that close specific, previously-missed classes as they're found (reactive, not preventive — each gate exists because something got past 4-6 rounds of the human audit first), (b) an affordance-coverage tool that does not exist yet, and (c) periodic independent-model audits that remain the only thing that has ever caught the class the mechanical gates don't yet know to check for. "Robust enough to de-systematize" is fair for defect classes already caught once; it is not evidence the net has stopped missing classes it hasn't hit yet.

## Leg 5 — Method harvest

Durably-shaped, worth lifting into the recipes corpus:

1. **"Attack the harm, not the behaviour"** (row 1659/1661, the commit-before-suite-run rule). Five straight failures of "instruct workers to run suites in the foreground" (an instruction competing against a locally-reasonable in-context judgment every time) were fixed not by a sixth, stronger instruction but by making the failure mode harmless: commit before any suite run, so a worker that backgrounds a long suite and stops loses only re-derivable output, not hours of uncommitted work. Explicitly generalized on the record: "when a behaviour recurs across independent agents despite explicit instruction, stop trying to suppress the behaviour and find what makes its recurrence cheap." This is a clean, reusable shape — asking a prompt to win against a reasonable local judgment (ADR-0011 Rule 4's "a prompt cannot be a net") is a category error every project using worker dispatch will hit.
2. **Apex/bottleneck review over per-item review, for whole-cycle diffs** (row 140, success-story ledgered with the mechanism named): one reviewer examines an entire cycle's diff together rather than one review per commit — caught a real cross-commit interaction defect (`limit=0` backend validation silently breaking `limit=0` frontend messaging, landed ~1 minute apart) invisible to any single-diff review, "no matter how careful." Reused deliberately across this whole window (the round-2/sprint-3 "apex" review shape, rows 2194-2198).
3. **Reviewer non-front-loading, held as a discipline against itself**: row 1298, an auditor dispatch that told the second-pass auditor to compare against the first pass's named findings was killed and relaunched with the exact original prompt — "voiding any claim of independent judgment" is stated as the reason, not merely a rule cited. The before/after comparison is explicitly reserved as the **orchestrator's own** job, never delegated to either auditor (repeated at rows 1461, 1478, 1501).
4. **Negative-control witnessing as standard practice**, not just for gates: reviewers reproduce claims from scratch rather than trust self-reports (explicit ADR-0013 Rule 5 citation, rows 1006, 1077, 1081, 1096, 1532) — e.g. row 1532 independently re-runs the exact decoder against both old and new config shapes to confirm accept/refuse behavior, rather than trusting reported exit codes.

Recurring-but-unclassifiable shapes, flagged as such per the standing method-harvesting posture (may not know what we're looking for):

- A **repeated self-correction pattern where the correction itself becomes the finding**: rows 1347 (scheduler-avoidance), 1451 (authorization overreach), 1176/1185 (missing blocks-close edge), 29e7d5b (stale precedence caveat) are all instances of the *same* underlying shape — an orchestrator under time/quota pressure reverts to hand judgment over a mandated/mechanized tool or boundary, and is caught either by the maintainer directly or by a dispatched reviewer, months apart, in structurally identical form each time. Whether this is "insufficient enforcement of the mandated-tool rule" or "an irreducible property of judgment-based orchestration under pressure" is not resolved anywhere in the record — flagging it as a shape rather than a single incident, since the current mitigations (row:147's "mandated" tag, row:1465's explicit-model-parameter rule) are all *instruction*-shaped fixes to a problem the project's own row-1659 method (above) says instructions don't reliably fix.
- The **"informs vs blocks-close gates close not start"** gap (Leg 1) is the same shape at the kernel-design level rather than the orchestrator-judgment level — worth autoharn treating as a standing kernel-doctrine question (does the kernel want a start-time refusal primitive at all, or is "gates close not start" a deliberate design choice whose cost this project has now hit three times) rather than a one-off panel finding.
